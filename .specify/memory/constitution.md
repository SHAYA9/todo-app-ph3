# Phase IV Constitution – Local Kubernetes Deployment (Minikube)

## Core Principles

### I. Spec-Driven Infrastructure (NON-NEGOTIABLE)
All infrastructure must be defined via specifications.
No manual Dockerfiles, Kubernetes manifests, or Helm charts are allowed.
All artifacts must be generated by Claude Code.

### II. Application Code is Immutable
The existing Phase III Todo Chatbot codebase must not be modified.
This phase focuses strictly on deployment and infrastructure.

### III. Containerization First
Frontend and backend applications must be containerized using Docker.
Use Docker AI Agent (Gordon) if available; otherwise generate standard Docker artifacts.

### IV. Kubernetes via Helm
All Kubernetes resources must be deployed using Helm charts.
Raw kubectl apply is prohibited unless generated via AI tooling.

### V. AI-Assisted DevOps
kubectl-ai and kagent must be used for Kubernetes operations, diagnostics, and optimization.
AI-generated commands must be documented.

### VI. Local Cluster Only
Deployment target is Minikube.
No cloud providers are allowed in this phase.

## Constraints
Technology Stack: Docker Desktop, Minikube, Helm 3+, kubectl-ai, kagent. Prohibited: Cloud providers in this phase, manual ops. Environment: WSL2 on Windows if needed. Compliance: Free tiers only. Deployment Policies: Single Helm chart for app; values.yaml for configs.

## Development Workflow
Refine spec → Generate plan/tasks via Claude Code.
Implement: Use AI tools to create Dockerfiles/Helm.
Test: Local Minikube deploy, smoke tests (e.g., access chatbot).
Review: Verify against constitution; track iterations in specs history.
Quality Gates: 80% test coverage, no crashes on basic ops, kagent health check pass.

## Governance
This constitution supersedes all prior development practices.
Any change requires spec refinement and regeneration.
